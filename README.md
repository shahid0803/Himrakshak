# HimRakshak

**An offline-first, software-only landslide monitoring and early-warning prototype for mountainous regions.**

HimRakshak demonstrates how virtual slope-monitoring stations can send sensor-like readings to a dashboard, receive an explainable demonstration risk assessment, and simulate communication failures. The project is designed as an academic and hackathon prototype—not as a field-deployed or life-critical warning system.

> **Project status: Phase 11 deployment-ready.** The local application, improved dashboard, Python backend, three-station simulator, software reliability controls, tests, Wokwi starter files, and Render deployment configuration are included. A live Render URL is created only after the repository owner applies the Blueprint; Wokwi-to-cloud networking is not implemented.

## Important: What this project is—and is not

- Sensor readings are generated by software or entered as simulated Wokwi packets. They are not measurements from physical slope sensors.
- Risk levels are produced by an explainable, illustrative rule-based model. They are not generated by machine learning and have not been scientifically calibrated or validated for real slopes.
- Communication fault controls simulate software-level packet behavior. They do not test LoRa radio range, radio interference, or real-world packet delivery.
- The Wokwi ESP32 sketch currently prints JSON readings to the Serial Monitor. You must copy a line into the dashboard manually; live Wi-Fi/HTTPS transmission is not implemented in the current sketch.
- No physical LoRa/SX1262 hardware integration or active cloud deployment is included in the current project.

**Do not use HimRakshak to make real-world evacuation, road-closure, or public-safety decisions.**

## Implemented features

### Dashboard

- Improved, responsive, single-page dashboard in `index.html`.
- Standalone browser simulation that can run without the Python backend.
- Sensor cards and visualizations for soil moisture, tilt, vibration, and battery.
- Demonstration risk level, score, and rule-based explanations.
- Three virtual station profiles: `HR-01`, `HR-02`, and `HR-03`.
- Scenario controls, event history, packet import, and CSV export.
- Backend-connected mode when served by the local Python application.

### Python backend

- Python standard-library HTTP server; no third-party runtime packages are required.
- Reading schema validation and backend-side risk reassessment.
- Three independent in-memory virtual stations with separate scenarios, sequence counters, latest readings, and histories.
- Deterministic simulator scenarios: `normal`, `heavy_rain`, `slope_shift`, and `vibration_burst`.
- Software-only reliability operations: drop, delay, release, deliver, duplicate, stale, disconnect, and reconnect.
- Incoming device sequence preservation; duplicate and out-of-order packets are rejected without replacing accepted station state.
- Request-body size limit of 64 KiB and an allowlist of the three registered station IDs.
- In remote mode, a configurable per-station ingestion interval (default 3 seconds) and administrative protection for mutation/fault-injection routes.
- Bounded in-memory event history. Data is not persisted to a database and is lost when the server process restarts.

## Getting started locally

### Prerequisites

- Python 3.10 or newer.
- A modern browser such as Chrome, Edge, or Firefox.
- Git, if you want to clone the repository.

No `pip install` step is required. The project currently uses only the Python standard library. `requirements.txt` is retained for project setup clarity.

### Clone the repository

```bash
git clone https://github.com/shahid0803/Himrakshak.git
cd Himrakshak
```

### Run the dashboard and backend together

From the project root:

```bash
python -m himrakshak.server
```

Open the dashboard:

```text
http://127.0.0.1:8765/
```

The server binds to `127.0.0.1` by default and serves the dashboard and API from the same origin. Stop it with `Ctrl+C`.

To use another local port:

```bash
python -m himrakshak.server --port 9000
```

Then open `http://127.0.0.1:9000/`.

### Run the dashboard without the backend

You can also open `index.html` directly in your browser. This starts the standalone browser simulation. Backend-only reliability controls will not be available in this mode.

## Run the simulator from the command line

Generate one normal reading:

```bash
python -m himrakshak.simulator --scenario normal
```

Generate three heavy-rain scenario readings with a reproducible random seed:

```bash
python -m himrakshak.simulator --scenario heavy_rain --count 3 --seed 42
```

Available scenarios:

- `normal`
- `heavy_rain`
- `slope_shift`
- `vibration_burst`

The simulator outputs JSON Lines containing a reading and a separate risk assessment. Values and scores are for demonstration only. See [`docs/risk-model.md`](docs/risk-model.md) for the scoring formula and thresholds.

## Run the tests

Run the full test suite from the project root:

```bash
python -B -m unittest discover -s tests -v
```

Run the end-to-end HTTP acceptance test separately:

```bash
python -B -m unittest tests.test_demo_acceptance -v
```

The Phase 11 handover retains the previously verified 111 unit/integration test cases, 118 subtests, and separate passing acceptance test. Re-run the commands above on your own checkout to verify its current state.

## API overview

When the local server is running, useful read-only endpoints include:

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Service health and model metadata |
| `GET` | `/api/state` | Latest accepted result and bounded event history |
| `GET` | `/api/stations` | Three-station roster and summaries |
| `GET` | `/api/stations/HR-01` | Details and history for one station |

The backend also provides reading ingestion, scenario simulation, and station-specific software reliability endpoints. See [`docs/api-contract.md`](docs/api-contract.md) for request/response formats, endpoint details, validation rules, and errors.

## Security and remote/cloud mode

### Local mode (default)

- Binds to `127.0.0.1:8765` by default.
- Does not expose the service to the public network.
- Local mutation and fault-simulation routes are available for development and demonstrations.

The server rejects a public bind address unless remote mode is explicitly enabled.

### Remote mode (deployment configuration)

The remote-mode command is:

```bash
python -m himrakshak.server --allow-remote
```

It binds to `0.0.0.0` and uses the hosting platform's `PORT` environment variable (defaulting to `10000` when not supplied). The `render.yaml` file contains a Render Web Service Blueprint configuration and uses `/api/health` as the health-check path.

Remote-mode controls include:

- `HIMRAKSHAK_ADMIN_KEY`: required to enable protected mutation/fault-injection routes. Requests must send the `X-HimRakshak-Admin` header. If the key is absent in remote mode, those mutation routes are disabled.
- `HIMRAKSHAK_INGEST_MIN_INTERVAL_SECONDS`: minimum time between accepted readings per station; defaults to 3 seconds in remote mode.
- `PORT`: assigned by the hosting platform.
- `PYTHONUNBUFFERED`: set to `1` in the included Render configuration.

**Important security limitation:** The public reading-ingestion endpoint does not authenticate the sender in this prototype. Station allowlisting, schema validation, sequence checks, payload limits, and rate limiting are not a substitute for device authentication. A public deployment can be spoofed or have its demo readings manipulated. Treat any deployment as a temporary demonstration only; do not send sensitive information or rely on it for safety decisions. Never put `HIMRAKSHAK_ADMIN_KEY` in `index.html`, browser JavaScript, or a public Wokwi sketch.

### Deployment status

The application is ready for manual Render deployment through `render.yaml`. The repository does not claim a public backend URL until the Blueprint has been applied and the post-deployment checklist in [`docs/deployment.md`](docs/deployment.md) passes.

The server stores station state and event history in process memory (up to 100 events per station). There is no database or persistent storage, so state resets when the process restarts or the hosting service is recycled. Free hosting plans may also sleep or have cold starts; check the provider's current limits before a presentation.

### Manual Render deployment

1. Sign in to Render and choose **New → Blueprint**.
2. Connect `shahid0803/Himrakshak` and select the `main` branch.
3. Review the `himrakshak` web service loaded from the root `render.yaml`.
4. Keep the **Free** plan, allow Render to generate `HIMRAKSHAK_ADMIN_KEY`, and apply the Blueprint.
5. Wait for the deploy and health check to complete, then use the HTTPS service URL shown by Render.
6. Run the endpoint checklist in [`docs/deployment.md`](docs/deployment.md); do not record or invent a URL before deployment.

## Wokwi virtual ESP32 demonstration

The starter circuit and sketch are in [`wokwi_esp32_demo/`](wokwi_esp32_demo/).

1. Open [Wokwi ESP32](https://wokwi.com/esp32).
2. Create an ESP32 project.
3. Copy `wokwi_esp32_demo/sketch.ino` into the sketch editor.
4. Replace the Wokwi circuit JSON with `wokwi_esp32_demo/diagram.json`.
5. Start the simulation and open Serial Monitor at 115200 baud.
6. Adjust the potentiometers and press the button to change simulated values.
7. Copy a complete JSON line from Serial Monitor and import it into the dashboard.

The current sketch uses simulated inputs and Serial output. Importing a packet into the dashboard is a manual copy/paste step. Wi-Fi, HTTPS posting, live cloud integration, and SX1262/LoRa communication are not implemented in this version. Detailed steps and control mappings are in [`wokwi_esp32_demo/README.md`](wokwi_esp32_demo/README.md).
